Project Overview: The "Titan" Terrain Engine

You are building a cross-platform C++ terrain engine designed specifically to bridge the gap between macOS and high-end procedural generation.

What is being built:

    libTitanCore (The Brain): A pure C++ library that handles the heavy math—noise generation, hydraulic erosion, thermal weathering, and mesh triangulation. It has no UI and no engine dependencies.

    TitanLab (The Standalone App): A lightweight macOS application built with Metal and Swift/C++. This is your "creative sandbox" where you tweak sliders and see terrain evolve in real-time without the overhead of Unreal Engine.

    TitanBridge (The Unreal Plugin): A C++ wrapper that allows Unreal Engine to call libTitanCore. It takes the generated data and feeds it into Unreal’s rendering system using the Procedural Mesh Component.

1. Math & Algorithm Resources

Terrain generation isn't just "noise"; it's a sequence of geological simulations.[1]

The "Bible" of Noise: The Book of Shaders (Chapter 13: Fractal Brownian Motion). This explains how to stack Perlin/Simplex noise layers to create "fBm," which gives terrain its natural, self-similar look.

Ridged Multi-Fractal Math: For sharp, Alpine-style peaks, you need "Ridged Multi-fractal" noise. Search for "Musgrave Ridged Multi-fractal" to find the standard algorithm used by Gaea and World Machine.

Hydraulic Erosion (The most important step):

The Particle Method (Easier): Look for Sebastian Lague’s "Coding Adventure: Hydraulic Erosion".[1] He provides a clear explanation and pseudocode for the "droplet" method.

The Pipe-Model Method (Faster/Pro): Read the seminal paper "Fast Hydraulic Erosion Simulation and Visualization on GPU" by Mei et al (2007). It explains how to treat water like a "layer" that flows through pipes between cells.[1]

Thermal Erosion: This simulates "talus slopes" (rocks falling down a cliff until they hit a stable angle).[1][2] Search for the "Angle of Repose Algorithm" or "Thermal Weathering."

2. Essential C++ Libraries (Mac Compatible)

Don't write every math function from scratch. These libraries are highly optimized for Mac:

Noise Logic: FastNoise2.[1] This is the gold standard. It uses SIMD (NEON for Apple Silicon) instructions, making it significantly faster than standard Perlin noise libraries.[1]

Vector Math: GLM (OpenGL Mathematics).[1] It’s a header-only C++ library that handles all the 3D math (vectors, matrices) identically to how shaders do.

UI Framework: Dear ImGui. Use this for your sliders and nodes.[1] It has a native Metal backend for your standalone Mac app and works perfectly inside Unreal.[1]

3. Professional PBR Texture Libraries

Since you are procedural, you won't "paint" textures; you will "Splat Map" them based on height and slope.[1] You need high-quality Ground, Rock, Grass, and Snow textures.

Poly Haven: 100% free, high-quality PBR terrain textures.[1]

AmbientCG: Thousands of seamless CC0 textures.[1]

3DTextures.me: Great source for specific rock and cliff textures.[1]

4. Advanced Shading Techniques (To Avoid "Tiling")

Standard textures look like a repeated grid from far away.[1] Use these techniques to make your terrain look professional:

Triplanar Mapping: Since procedural terrain doesn't have UV coordinates, Triplanar Mapping projects textures from the X, Y, and Z axes to avoid stretching on cliff faces. Catlike Coding has the best conceptual breakdown of this.

Stochastic Sampling: This is a modern trick that "jitters" the texture to completely hide the grid-like tiling pattern. Search for "Histogram-Preserving Blending" or "Stochastic Texture Tiling."[1]

2. Memory Layout: The Heightfield Container

A common mistake is using a 2D array (e.g., float terrain[x][y]). This causes "cache misses" and destroys performance.

The Solution: Use a 1D Flat Array representing 2D space.

std::vector<float> heightMap(width * height);

Accessing Data: To get height at (x, y), use index = y * width + x;.

Memory Alignment: Since you will be using SIMD (Apple NEON) for math, align your memory to 16 or 32-byte boundaries. This allows the CPU to load data into registers much faster.

3. The Noise Engine (FastNoise2 Integration)

Standard perlin() functions are too slow. You will integrate FastNoise2, which uses SIMD instructions.

The Pipeline: Create a "Noise Tree."

Base Shape: Simplex Noise (low frequency) for continents.

Detail: Fractal Brownian Motion (fBm) with 6–8 octaves for cragginess.

Modifier: A "Generator" that uses a Ridged fractal for mountain peaks.

Apple Silicon Optimization: Ensure FastNoise2 is compiled with NEON support enabled. This allows an M3 chip to calculate 4 noise values in a single CPU cycle.

Potential Pitfalls & Workarounds
Pitfall A: The "Binary Incompatibility" (Unreal vs. System C++)

The Issue: Unreal Engine uses its own memory allocator and a specific version of the C++ standard library. If your libTitanCore is compiled with a different version of libc++ than Unreal, the plugin will crash when passing a std::vector between them.

Workaround: Never pass complex C++ containers (like std::vector or std::string) across the library boundary. Instead, pass raw pointers and size variables.

Bad: void Process(std::vector<float> data);

Good: void Process(float* data, int size);

Pitfall B: Floating Point Determinism

The Issue: You might generate a terrain on your Mac that looks slightly different when generated on a friend's Windows PC, even with the same seed. This happens because different compilers handle floating-point math differently.

Workaround: Use std::floor and explicit casting. Avoid using fast-math compiler flags, as they trade accuracy (and determinism) for speed.

Pitfall C: The "Edge Seam" Problem

The Issue: When you move to "Infinite" terrain later, you will generate chunks (e.g., Chunk A and Chunk B). If the noise is calculated per-chunk, the edges won't match, creating visible cracks.

Workaround: Your noise function must use Global Coordinates, not local ones. Instead of asking for "height at x=10 in this chunk," ask for "height at world_x=5010."

Pitfall D: Thermal Throttling on MacBooks

The Issue: Calculating heavy erosion and noise in a loop will spike the CPU to 100%, causing the Mac to throttle (slow down) after a few minutes.

Workaround: Implement Task-Based Multithreading. Instead of one giant loop, break the terrain into "tiles" (e.g., 32x32 areas) and use a thread pool. This is more energy-efficient and keeps the UI responsive.

Pitfall E: Normal Calculation at Edges

The Issue: To calculate a "Normal" (which direction the ground faces), you need to look at the neighbors of a vertex. At the edge of your heightmap, there are no neighbors, leading to flat lighting at the edges of your terrain.

Workaround: Generate a heightmap that is 2 pixels larger than your mesh (e.g., 1026x1026 for a 1024x1024 mesh). Use the "hidden" outer pixels only for normal calculations so the edges look perfectly shaded.

Phase 2: The Standalone App (The Laboratory — TitanLab)

The goal of Phase 2 is to build a high-performance macOS application that serves as a "Creative Sandbox." This app allows you to manipulate the parameters of your libTitanCore (from Phase 1) and see the results instantly. Because it is built with Metal (Apple’s native graphics API), it will be significantly faster and more responsive than working inside the heavy Unreal Engine Editor.

1. The Tech Stack: The "Bridge" Architecture

To build a modern Mac app that uses a C++ library, you must use a "sandwich" of languages:

Swift/SwiftUI: For the window management, menus, and file saving.

Objective-C++ (.mm): This is the critical bridge. Objective-C++ can talk to both Swift and pure C++. You will use this to pass data from your UI sliders to your libTitanCore.

Metal (MSL): The shading language used to render the 3D terrain on the GPU.

2. Integrating Dear ImGui with Metal

You do not want to build custom sliders in SwiftUI for every terrain parameter; it is too slow for 3D tools. Instead, you will integrate Dear ImGui.

Setup: Use the imgui_impl_metal and imgui_impl_osx backends provided in the ImGui repository.

Layering: The app will render the 3D terrain first, and then "draw" the ImGui interface on a transparent layer on top.

The Workflow: When a user moves a slider in ImGui (e.g., "Erosion Strength"), the variable is updated in C++, which triggers a re-generation of the heightmap in libTitanCore.

3. The Metal Pipeline: Getting Data to the GPU

Your C++ library produces a list of vertices. You need to get these into the Mac's GPU memory.

The Vertex Buffer: Use MTLDevice.makeBuffer. To keep the app fast, use Shared Storage Mode (MTLResourceStorageModeShared). On Apple Silicon, this allows the CPU and GPU to share the same physical memory, eliminating the need to "upload" data over a bus.

The Shader: Write a simple Metal Vertex/Fragment shader.

Vertex Shader: Positions the terrain points in 3D space and calculates simple lighting based on the normals generated in Phase 1.

Fragment Shader: Colors the terrain. Use a "Slope Debugger" (coloring steep areas red and flat areas green) to help you visualize if your erosion is working.

4. The Real-Time Update Loop

To keep the app from freezing during heavy generation:

UI Thread: Handles the mouse and sliders.

Worker Thread (GCD): Calls libTitanCore::GenerateHeightfield().

Completion Handler: Once the C++ is done, it signals the Metal View to update its buffers and redraw.

Potential Pitfalls & Workarounds
Pitfall A: The "Swift-to-C++" Boundary

The Issue: Swift cannot directly call C++ functions that use standard library types (like std::vector).

Workaround: Create an Objective-C++ wrapper class (TitanBridge.mm). Swift calls the wrapper, and the wrapper calls the pure C++ library. Use void* or raw pointers to pass the heightmap data back to the Swift/Metal side.

Pitfall B: Coordinate System Mismatch (Y-Up vs. Z-Up)

The Issue: Unreal Engine is Z-Up (Z is height). Metal and most macOS frameworks are Y-Up (Y is height). If you aren't careful, your terrain will be standing up like a wall in your standalone app but lying flat in Unreal.

Workaround: Standardize libTitanCore to use Y-Up (mathematical standard). In the Phase 4 Unreal Bridge, perform a single rotation swap: UnrealPos = FVector(Core.x, Core.z, Core.y).

Pitfall C: Viewport Resize Crashes

The Issue: When you resize the app window, the Metal "Drawable" size changes. If your ImGui or Metal buffers are mid-draw, the app will crash with a MTLTargetSizeMismatch error.

Workaround: Use a MTKViewDelegate. Inside the drawableSizeWillChange method, pause the renderer, recreate your depth textures and buffers to match the new window size, and then resume.

Pitfall D: GPU Overload (The "Hang")

The Issue: If you try to render a 4096x4096m mesh with complex erosion every time a slider moves, the Mac's GPU will hang, and macOS will kill the app ("The GPU has been reset").

Workaround: Implement "Deferred Update." Don't regenerate the terrain while the slider is moving. Wait until the user releases the mouse button (using ImGui::IsItemDeactivated()) before triggering a high-resolution re-generation.

Pitfall E: Apple Silicon "Unified Memory" Pitfall

The Issue: Even though memory is shared, if the CPU is writing to the heightmap buffer while the GPU is trying to read it to draw the frame, you will get "tearing" or flickering.

Workaround: Use Triple Buffering. Create three separate Metal buffers. The CPU writes to Buffer 1, while the GPU reads from Buffer 3. They rotate every frame. This ensures the GPU never reads "half-finished" terrain data.

Success Metric for Phase 2

By the end of this phase, you should have a .app file on your Mac where you can:

Drag a slider and see a 3D mountain shape change shape in real-time.

Fly a camera around the terrain using WASD keys.

Click an "Export" button to save the current terrain as a 16-bit Heightmap.

This confirms your C++ logic is solid before you ever touch the complexities of the Unreal Engine API.

Phase 3: The Simulation (Geology & Erosion Algorithms)

In this phase, you transform "mathematical noise" into "realistic geology." This is the most computationally expensive part of the project. You are writing the algorithms that simulate millions of years of rain and gravity in a few seconds.

1. Hydraulic Erosion (The Particle/Droplet Model)

If the droplet slows down or hits a depression, add height back to the heightmap (Deposition).

Evaporate: Reduce the droplet's water volume. When it reaches zero, or goes off-bounds, destroy it.

The Math of "Inertia": Crucial for realism. The droplet shouldn't just turn 90 degrees instantly; it should have momentum, allowing it to "carve" through small ridges and create curved riverbeds.

2. Thermal Weathering (The Talus/Scree Model)

While hydraulic erosion creates vertical canyons, thermal weathering creates the "smooth" sloped piles of rock at the base of cliffs.

The Angle of Repose: Define a constant (e.g., 30 degrees).

The Algorithm: Iterate through every pixel. Compare its height to its four neighbors.

If the height difference is greater than your "Angle of Repose" threshold, move a percentage of the material from the higher pixel to the lower pixel.

Repeat this pass 10–50 times to simulate the "settling" of loose soil.

3. Apple Silicon Parallelization (GCD)

Running 500,000 droplet simulations on a single CPU core is slow. On a Mac, you must use Grand Central Dispatch (GCD) or std::jthread to utilize all M-series Performance and Efficiency cores.

Atomic Heights: Since multiple threads might try to erode the same pixel simultaneously, you must use Atomic Floats (available in C++20) or a "Layered Update" system to prevent "Race Conditions" where two droplets cancel each other out.

Potential Pitfalls & Workarounds
Pitfall A: The "Local Minima" (Pitting)

The Issue: Droplets get stuck in small "holes" in the noise. They stop moving, deposit all their sediment in a single pixel, and create ugly "spikes" or pits in the terrain.

Workaround: Implement "Pit Filling" or "Sediment Pooling." When a droplet stops in a hole, it should "fill" the hole with water until it reaches the level of the lowest neighbor, then continue moving.

Pitfall B: The "Staircase" Artifact

The Issue: If your erosion math is too aggressive, you will see a "staircase" pattern (terracing) along the slopes because the droplets are snapping to the grid pixels.

Workaround: Use Bilinear Interpolation for both reading and writing. When a droplet erodes, it should distribute the "damage" across the four nearest pixels based on its fractional distance from them, rather than just hitting one pixel.

Pitfall C: Thread-Safety Race Conditions

The Issue: Two droplets on different CPU threads try to modify heightmap[500] at the exact same microsecond. One update is lost, leading to "ghost" artifacts or software crashes.

Workaround: Instead of locking the whole heightmap (which is slow), use a Lock-Free approach. Let threads write to a private "Delta Buffer." Once all droplets are finished, merge the Delta Buffer back into the Main Heightmap in one single-threaded pass.

Pitfall D: Float Precision Loss

The Issue: After 1,000,000 droplets, the small subtractions (height -= 0.0001f) can lead to floating-point drift, where the terrain eventually loses its "fine" detail or becomes "jittery."

Workaround: Perform all erosion calculations in Double Precision (double) and only cast back to float when sending the data to the GPU (Metal) or Unreal Engine.

Pitfall E: The "Memory Wall" (Cache Locality)

The Issue: Randomly spawning droplets across a 4K heightmap causes "Cache Misses." The CPU spends more time waiting for RAM to send data than actually calculating erosion.

Workaround: Use Spacial Partitioning. Divide the terrain into 64x64 blocks. Assign a thread to a specific block. Spawn droplets within that block. This keeps the height data in the CPU’s L1/L2 Cache (which is extremely fast on M1/M2/M3 chips).

Success Metric for Phase 3

By the end of this phase, your standalone app (TitanLab) will show a dramatic difference:

Before: The terrain looks like "lumpy plastic" (pure noise).

After: You see "Flow Lines" (rivers), "Ridges" (mountains), and "Basins" (plains).

Performance: On an M-series Mac, a 1024x1024 terrain should finish 200,000 erosion iterations in under 1 second.

4. Asynchronous Execution (The Task Graph)

Running a 500,000-iteration erosion simulation on the Game Thread will cause the Unreal Editor to freeze and show the macOS "Spinning Beachball."

The Solution: Use FAsyncTask or the FFunctionGraphTask.

The Workflow:

User clicks "Generate."

Unreal spawns a background thread to call libTitanCore::RunErosion().

The Game Thread remains responsive (you can still move the camera).

Once the background thread finishes, it uses a Thread-Safe Callback to tell the Procedural Mesh Component to update.

Potential Pitfalls & Workarounds
Pitfall A: The "RPath" Linking Error

The Issue: On Mac, even if the plugin compiles, Unreal might fail to load it at runtime because it can’t find the .dylib path. You’ll see an "Image not found" error.

Workaround: Use a Static Library (.a) instead of a dynamic one whenever possible. If you must use a .dylib, use the install_name_tool command in a post-build script to set the @rpath/ to point inside the Plugin’s Binaries folder.

Pitfall B: Memory Alignment Crashes

The Issue: libTitanCore might use SIMD-aligned memory (Phase 1), but Unreal’s TArray (its standard list type) might not follow the same alignment rules. Passing data between them can cause a SIGBUS crash.

Workaround: Instead of passing a TArray into your Core, let the Core fill a raw float* buffer. Once done, use TArray::Append(RawPointer, Count) to copy the data into Unreal-managed memory.

Pitfall C: Scale Mismatch (The "Micro-Mountain")

The Issue: In TitanLab (standalone), 1.0 unit might be the whole mountain. In Unreal, 1.0 unit is 1 centimeter. Your mountain will appear as a tiny speck.

Workaround: Create a UnitsPerPixel UPROPERTY. Multiply your Core output by this value (usually 100.0 or 200.0) before feeding it into the vertex buffer.

Pitfall D: Collision Generation Lag

The Issue: When you update a ProceduralMeshComponent, Unreal tries to calculate complex 3D physical collisions. On a high-poly terrain, this can take 10 seconds, freezing the editor after the math is done.

Workaround: Disable "Simulate Physics" and "Create Collision" during the iterative design phase. Only trigger a bCreatePhysicsState update when the user clicks a specific "Finalize Collision" button.

Pitfall E: The "Invalid Bounds" Glitch

The Issue: If you don't manually update the Actor's Bounds, Unreal might think the terrain is at 0,0,0 with a size of 0. As soon as you look away from the origin, the terrain will disappear (Frustum Culling).

Workaround: After updating the mesh, call ProceduralMeshComponent->UpdateBounds() and SetComponentTickEnabled(false) to ensure Unreal correctly calculates the visibility of the new geometry.

Phase 5: Shading & Material Logic (The Visual Finish)

In this final phase, you move away from "grey-box" geometry and create a professional-grade environment. Since procedural terrain does not have traditional UV coordinates (you can't "unwrap" a mountain manually), you must use Procedural Shading—automatically applying textures based on the data generated by your C++ Core.

1. Generating Mask Data (The "Splat" Maps)

2. The Triplanar Material (The Anti-Stretch Solution)

Standard texture mapping on steep procedural cliffs looks stretched and ugly. You must implement Triplanar Mapping in the Unreal Material Graph.

The Logic: Instead of using UVs, the shader projects the texture from three directions (X, Y, and Z) and blends them based on the surface normal.

Implementation: In Unreal, use the WorldAlignedTexture node. This ensures that a rock texture on a vertical cliff face looks as sharp as the grass on the flat plains.

3. Advanced Layer Blending

To avoid "hard lines" between grass and rock, you need a "Height-Blend" shader.

The Tech: Use the Height Map included in your PBR textures (e.g., from PolyHaven).

The Math: Instead of a simple linear fade, the shader compares the height of the rock grains vs. the grass blades. This allows grass to "peek through" the gaps in the rocks, creating a significantly more realistic transition.

4. Runtime Virtual Texturing (RVT) for Mac Performance

Procedural materials are expensive for the GPU, especially on MacBooks with integrated memory.

The Solution: Use Unreal's Runtime Virtual Texturing.

How it works: Unreal "bakes" your complex, multi-layered procedural material into a flat texture in the GPU memory at runtime.

Result: Even if your material has 10 layers of textures and complex math, the Mac GPU only has to render one single texture, boosting your frame rate from 30 FPS to 100+ FPS.

Potential Pitfalls & Workarounds
Pitfall A: The "Tiling" Grid Pattern

The Issue: When you look at a large landscape, you see a repeating "checkerboard" pattern of grass textures.

Workaround: Implement Distance-Based Tiling. Use two versions of the same texture: one small (for detail up close) and one large (for the far distance). Use the PixelDepth node to blend between them, which breaks up the visual repetition.

Pitfall B: Metal Shader Instruction Limits

The Issue: Apple’s Metal API has a limit on how complex a single material can be. If you stack too many textures (Grass, Rock, Snow, Sand, Mud), the shader will fail to compile or will be extremely slow.

Workaround: Use Texture Arrays or RVT. Alternatively, limit your procedural blending to 3-4 "Core" layers and use Vertex Colors to mask them efficiently.

Pitfall C: Tangent Space Mismatch

The Issue: Normal maps on procedural meshes often look "inverted" or have weird lighting seams because the Procedural Mesh Component doesn't generate "Tangents" automatically.

Workaround: In your Phase 4 C++ code, you must call UKismetProceduralMeshLibrary::CalculateTangentsForMesh. This ensures the Rock and Grass textures react to Unreal's lights (Lumen) correctly.

Pitfall D: Large World UV Jitter

The Issue: When using World Position for texturing (Triplanar), the textures might "jitter" or "swim" when the camera moves very far from the center of the world.

Workaround: Use Camera-Relative World Position. Subtract the Absolute World Position from the Camera Position in the material graph to keep the math within a range that floating-point numbers can handle accurately.

Pitfall E: The "Glassy" Terrain (Missing Roughness)

The Issue: Procedural terrain often looks like wet plastic because people forget to map the "Roughness" and "Ambient Occlusion" channels.

Workaround: Ensure your C++ Core generates a "Moisture Map" (from the erosion data). Use this in the Material to make riverbeds look "Wet/Shiny" (Low Roughness) and mountain peaks look "Dry/Matte" (High Roughness).

This final list serves as your "Engineering Manual." It contains the academic foundations for the math, the technical documentation for the libraries, and the practical guides for implementing them specifically on a Mac.

1. Academic Research & Math Foundations

To build a professional generator, you should move beyond "basic noise" and look at how simulation works in computer science.

Hydraulic Erosion (The Pipe Model): Fast Hydraulic Erosion Simulation and Visualization on GPU (Mei et al.). This is the seminal paper for modern erosion. While it focuses on GPU, the logic is the gold standard for C++ implementation.

The Particle Model: Implementation of a Method for Hydraulic Erosion (Hans Beyer). This is the best resource for the "Droplet" method used in Phase 3.

Noise Theory: Simplex Noise Demystified (Stefan Gustavson). A deep dive into why Simplex noise is superior to Perlin noise for 3D terrain.

The Book of Shaders (Noise Chapter): The Book of Shaders - Noise. Excellent visual explanations of Fractal Brownian Motion (fBm) and how layers of noise create "natural" shapes.

2. Library Documentation

These are the tools you will be linking into your libTitanCore.

FastNoise2 Wiki: FastNoise2 GitHub Wiki. This is where you learn how to use the "Noise Tree" to combine different types of noise (e.g., mixing Ridged peaks with Perlin valleys).

GLM (OpenGL Mathematics): GLM Manual. Since you are on Mac, you need a math library that matches shader logic. GLM is the industry standard for C++ vector/matrix math.

Dear ImGui: ImGui Wiki & Examples. Specifically, look at example_apple_metal to see how to bridge the UI with the Mac's graphics API.

CMake Documentation: CMake Tutorial. Essential for learning how to compile your library for both Intel and Apple Silicon (Universal Binaries).

3. Unreal Engine Technical Docs

Use these for building the "Bridge" in Phase 4.

Procedural Mesh Component: Official UE API Reference. Pay close attention to the CreateMeshSection and UpdateMeshSection functions.

Unreal Task Graph: Multithreading with Task Graph. This documentation explains how to run your erosion math on a background thread so the Mac doesn't freeze.

Runtime Virtual Texturing (RVT): UE RVT Documentation. Learn how to optimize your terrain rendering for Mac GPUs.

LWC (Large World Coordinates): UE5 LWC Overview. Critical if you plan on making "infinite" or very large terrains to avoid floating-point jitter.

4. macOS & Metal Development

Since you are developing on a Mac, these resources handle the "Metal" side of Phase 2.

Metal Developer Documentation: Apple Metal API.

Metal Best Practices: Apple Unified Memory Optimization. This explains how to use the M1/M2/M3 "Unified Memory" to pass heightmaps between the CPU and GPU without copying data.

Objective-C++ Bridging: Mixing Objective-C, Swift, and C++. You will need this to build the UI for your standalone TitanLab app.

5. Educational Blogs & Practical Tutorials

The most useful "Step-by-Step" logic guides (even if they use different languages, the logic is 100% portable to your C++ Core).

Red Blob Games: Polygonal Map Generation. The absolute best resource for understanding how to turn noise into geographical features.

Sebastian Lague (YouTube/GitHub): Coding Adventure: Hydraulic Erosion. He provides a great C# implementation of the droplet method. Porting this to C++ is a fantastic exercise for Phase 3.

Catlike Coding: Procedural Landscapes. Highly detailed tutorials on mesh generation and triplanar mapping math.

Scratchapixel: Generating Terrains with Noise. A math-heavy look at how to build the "grid" that forms your heightmap.

Final Project Checklist for Success:

IDE: Use JetBrains Rider for Mac or VS Code. (Standard Xcode is difficult for large Unreal C++ projects).

Compiler: Use Clang (default on Mac).

Versioning: Use Git. Procedural generation involves a lot of trial and error; you will want to "roll back" when your erosion algorithm accidentally turns your mountain into a flat plane.

Hardware: Test frequently on Battery vs. Plugged In. M-series Macs throttle differently when unplugged; ensure your erosion multithreading doesn't drain the battery in 5 minutes.

You are now ready to begin Phase 1. Start by setting up your CMake project and getting FastNoise2 to generate a simple array of numbers. Good luck!
